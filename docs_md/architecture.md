# Architecture

Noted is a Tauri 2.x app: a Rust backend (`src-tauri/`) and a React 18 +
TypeScript + Tailwind v4 frontend (`src/`), talking over Tauri commands
(frontend → backend) and events (backend → frontend). Type-safe bindings are
generated by **tauri-specta** into `src/bindings.ts` — but note that this file
is often **hand-maintained** between dev runs (see
[dev-workflow.md](dev-workflow.md#bindings)).

## Core pipeline

```
mic → cpal recorder → VAD (Silero) → streaming or batch ASR (transcribe-cpp / transcribe-rs)
    → dictation: paste into focused app (+ optional LLM cleanup)
    → meeting:   save to history → LLM notes → action items → todos/calendar
```

## Backend module map (`src-tauri/src/`)

Managers (long-lived, created at startup, held in Tauri state as `Arc<...>`):

- `managers/audio.rs` — device enumeration, recording, resampling, VAD
  integration; feeds real-time frames to the transcription stream router.
- `managers/model.rs` — ASR model catalog (`catalog/catalog.json`), download
  (with sha256/partial-file handling), discovery of custom GGUFs in the models
  dir, capability metadata. The speaker-diarizer model is **not** in this
  catalog (it produces no text); it has its own downloader in `diarization.rs`.
- `managers/transcription.rs` — the heart. Loads/unloads engines
  (transcribe-cpp `Session` for Whisper-family/parakeet/nemotron GGUFs;
  transcribe-rs engines for ONNX models), runs batch transcription, and hosts
  the **streaming worker** (`run_stream_worker`) used by live meeting
  transcription. Contains the pause-reset logic, speaker-turn building, and
  `StreamTextEvent` emission. See [meetings.md](meetings.md).
- `managers/history.rs` — all SQLite access (`history.db`): transcription
  history, meeting entries, notes columns, todos, ask sessions, keyword
  search. See [data-and-storage.md](data-and-storage.md).

Feature modules:

- `actions.rs` — `TranscribeAction`: the start/stop state machine for a
  recording. `TranscriptionOutput` enum decides the sink:
  `Paste { post_process }` (dictation) vs `SaveToHistory` (meeting). The
  meeting save path applies speaker names, stores live notes, and spawns note
  generation.
- `meeting.rs` — `MeetingSession` state (tray readout ticker, live text
  mirror, captions toggle, user's live notes, speaker names), the
  `live_meeting.json` snapshot for MCP, begin/end lifecycle, and the
  `PENDING_*` statics that hand data from session end to the async save
  pipeline.
- `diarization.rs` — speaker separation. Downloads/loads the Sortformer
  diarizer and runs it in a batch-rerun worker thread. See
  [meetings.md](meetings.md#speaker-separation).
- `notes.rs` — LLM note generation from transcripts + the second LLM pass
  that extracts action items into todos/calendar events. Single-flight
  guarded. See [notes-and-ai.md](notes-and-ai.md).
- `ask.rs` — "Ask your notes" answers: keyword search over meeting notes,
  context assembly, LLM answer, `ask-answer` event.
- `voice_commands.rs` — trigger-phrase parsing of dictations ("add event…",
  "remind me to…") into todos/calendar events; runs before paste.
- `calendar.rs` — read side of GNOME calendar (Evolution Data Server via
  `gdbus`) for the Home screen's "Coming up" cards.
- `radar.rs` (Linux-only) — opt-in meeting detection via PulseAudio
  (`pactl`), desktop notification with a "record" action.
- `mcp.rs` — a hand-rolled stdio MCP server (`--mcp-serve`) exposing notes
  and the live meeting to Claude/Codex. See [integrations.md](integrations.md).
- `settings.rs` — `AppSettings` struct, defaults, load/save via
  tauri-plugin-store (`settings_store.json`), and **one-time migrations** for
  changed defaults (e.g. meeting-notes prompt upgrades).
- `shortcut/` — global shortcut registration (rdev) and most
  `change_*_setting` Tauri commands.
- `tray.rs` — single-writer tray icon/menu, meeting readout
  (`TrayIcon::set_title` renders next to the icon on GNOME), i18n via
  `tray_i18n`.
- `overlay.rs` — recording overlay window (GTK layer shell on Linux;
  `HANDY_NO_GTK_LAYER_SHELL=1` disables).
- `main.rs` — CLI parsing, single-instance forwarding, and the
  **GDK_BACKEND=x11 forcing** on GNOME Wayland (see gotchas).
- `cli.rs`, `signal_handle.rs` — CLI flags (`--toggle-meeting`, etc.) and the
  shared `send_transcription_input()` used by both signals and CLI.

## Frontend map (`src/`)

The app shell is a sidebar + main-view layout (post-redesign; the old
settings-first Handy UI lives on inside a modal).

- `App.tsx` — view routing (`home | notes | todos | history | ask`), all
  toast listeners (meeting saved/failed, notes status, voice commands,
  auto-organized items), pending meeting title for record-from-event.
- `components/shell/`
  - `ShellSidebar.tsx` — nav, ask-session list ("SEARCHES"), dictation status
    card, model selector, settings gear.
  - `HomeView.tsx` — greeting, start/stop meeting, calendar "Coming up" cards
    with per-event Record buttons, recent notes, bottom ask bar.
  - `LiveMeetingView.tsx` — the in-meeting screen: left notes pad, right
    live-transcript rail with speaker turns and the name-speakers card.
  - `RichNoteEditor.tsx` — TipTap v3 WYSIWYG editor that reads/writes
    Markdown (`tiptap-markdown`); used by the note detail page.
  - `AskView.tsx`, `TodosView.tsx`, `useMeetingState.ts`.
- `components/settings/` — the settings modal content; `notes/NotesSettings.tsx`
  is actually the **Notes library + note detail page** (naming is historical),
  `notes/NotesStyleSettings.tsx` is the notes-prompt editor,
  `SpeakerSeparation.tsx` is the diarizer toggle with download progress.
- `stores/settingsStore.ts` — Zustand store; maps each setting key to its
  `commands.change*Setting` call.
- `bindings.ts` — specta bindings (commands, events, types). Hand-edited;
  keep style identical to generated output.
- `i18n/locales/*/translation.json` — 24 locales; every key must exist in all
  of them (`scripts/check-translations.ts` enforces).
- `styles/theme.css` — the entire color system as light/dark token pairs.
  Never hard-code palette colors elsewhere.
- `overlay/` — the separate recording-overlay window entry.

## Key cross-cutting patterns

- **Command/event architecture**: any new backend capability = a
  `#[tauri::command] #[specta::specta]` function + registration in `lib.rs` +
  a hand-added entry in `bindings.ts` + (if streaming data) a typed event.
- **Single-flight guards**: long LLM jobs use `static IN_FLIGHT:
Lazy<Mutex<HashSet<i64>>>` (notes, ask) and atomic DB claims
  (`UPDATE … WHERE flag = 0`, check `rows == 1`) so duplicate triggers can't
  double-run. Copy this pattern for any new background job.
- **PENDING\_\* handoff**: meeting-scoped data that must survive session end
  until the async save (live notes, speaker names) goes through a
  `static PENDING_X: Lazy<Mutex<…>>` in `meeting.rs`, written by
  `end_session`, consumed once by the save path in `actions.rs`.
- **Settings migrations**: changing a default that users already have stored
  requires a one-time migration in `settings.rs` keyed on recognizing the old
  default text; an edited value is the user's and must be left alone.
